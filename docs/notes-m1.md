## 3. 性能实测（本机，非参考环境）

`write_bench`（fsync=on、value=64B、内存表 1GB 不触发 flush）：

| 档位 | QPS | P99 | 对照 S0 |
|---|---|---|---|
| batch=1 | 3184 | 0.580 ms | ≥2k ✓ / ≤10ms ✓ |
| batch=64 | 120667 | 0.802 ms | 加速比 37.9×（≥8× ✓） |

**这组数字只证明"结构没走错"，不能证明达标**：S0 的参考环境是 3 节点 NVMe 集群，
单机单进程的 QPS 与集群写共识 QPS 不是同一个量。真正的 PERF-01 验收在 M2 之后。

## 4. 三个值得记的取舍

**WAL 先于内存表**。写路径顺序反过来会让"WAL 失败但内存表已改"成为可能，那次写入会被
读取方看见却不在盘上——一个只在崩溃后才显形的数据不一致。顺序定死之后，WAL 失败即写入失败，
内存表保持干净。

**墓碑必须落 SST**。Delete 若只在读路径"跳过不写"，旧 SST 里的版本会在 flush 后复活。
所以墓碑是正经记录，参与归并，只是被 Scan 过滤掉。

**快照用拷贝而不是 MVCC**。SPEC-1 红线 3 只要求"迭代期间 flush 不影响结果集"，
不是完整快照隔离。拷贝内存表 + 记住当时的 SST 列表，用最小代价满足这项要求；
真正的多版本语义属于 M5 的 Percolator，现在做会提前引入版本链复杂度。

## 5. 踩过的坑（四类，都是真缺陷）

1. **CRC 覆盖范围算错**（BUG-0001）。`finish()` 里先追加条数再算 CRC，`body.size()` 已被撑大
   4 字节，校验范围少 4 字节。症状极具欺骗性：写入正常、读取正常、**只有重开时 Corrupted**。
   这类缺陷靠引擎层冒烟是抓不住的，必须有直接对 SST 文件断言自洽性的用例。
2. **Windows 不允许删除打开中的文件**。flush 里先删 WAL 段再关句柄，在 Linux 上侥幸能过。
   顺序改为"先关后删"，并在注释里写明原因——否则下一个人会"优化"回去。
3. **`rename` 不覆盖已存在文件**（Windows）。Manifest 第二次写就失败。改为先删目标再改名，
   并让清单可缺失：装载时若清单不存在则扫 `sst/` 目录，宁可多载不可漏载。
4. **表序号重号**。装载 N 张表后 `next_seq` 取了 `max(…, N)` 而非 `N+1`，下一次 flush 会覆盖
   已有表。这类 off-by-one 在"只 flush 一次"的用例里永远不出现，是多段写入才暴露的。

样板从 10 行降到 2 行。这说明检查阈值定得合理——它逼我把重复变成共享，而不是加白名单。

## 7. 交接给 M2

- **`Storage` 接口已定型**，M2 的 `PeerStorage` 需要在此基础上加 raft log 的读写，
  届时只扩展不收敛（协议 §6）。
- **WAL 目前为数据面服务**；raft log 的 WAL 若复用同一组件，需要补"段索引 + 按 index 定位"，
  这是 SPEC-1 与 SPEC-2 描述重叠的地方，开工前要先定是否共用实现（见 `docs/reuse-register.md` §4）。
- **`cf` 字段在 proto 里有两套建模**（`kv.proto` 枚举 vs `raft_cmdpb.proto` 字符串），
  M2 接入 RPC 前必须先统一，否则会写出一层纯转发的样板代码。
- **`Engine::create_reader` 是拷贝语义**：M2 高频读路径上会成为开销，届时与 ReadIndex 一起改。
